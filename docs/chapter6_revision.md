# 第6章 可视化系统与实车诊断平台设计

## 6.1 概述

故障诊断算法的最终价值体现在对机器人运行状态的在线监测与决策支持能力。一个完整的智能故障诊断系统不仅需要高性能的诊断模型，还需要配套的可视化交互平台，将诊断结果以直观方式呈现给操作人员，并提供运动控制、数据采集、故障模拟等辅助功能。本章围绕上述需求，设计并实现了可视化系统与实车诊断平台。

可视化系统的建设遵循"先远程轻量、后本地深度"的两阶段路线。第一阶段面向实验室环境下的快速调试与数据采集需求，开发了基于浏览器/服务器（Browser/Server, B/S）架构的 Web 远程控制台，提供运动控制、传感器监控和数据落盘功能，其优势在于跨设备零部署，任何终端通过浏览器即可接入机器人 IP 地址。第二阶段面向模型部署与实车在线诊断需求，开发了基于 Electron 框架的桌面端系统，核心目标是突破 Web 端在浏览器安全沙箱限制下**无法调用本地 C++ ONNX 推理引擎**的技术瓶颈，同时提供离线数据管理、实验历史记录等操作系统原生能力。

两套系统共用 ROS 通信后端（rosbridge WebSocket `:9090`），但承载于完全不同的技术架构之上：Web 端基于 React + Vite 构建，通过 HTTP `:8000` 服务加载；Electron 端基于主进程-渲染进程分离架构，通过 `file://` 本地文件加载。两者形成功能互补格局——Web 端负责**实验**，桌面端负责**诊断**——可根据部署场景灵活选用或并行使用。

## 6.2 Web 远程控制台设计

### 6.2.1 技术架构

Web 控制台采用 B/S 架构，前端基于 React 18 与 Vite 构建工具开发，通过 rosbridge WebSocket 协议直连机器人 IP 地址的 `:9090` 端口，实现与 ROS 话题的实时双向通信。静态页面与 REST API 由机器人上位机运行的 `web_dashboard_server.py` 节点托管，监听 `:8000` 端口，形成完整的浏览器-服务器交互链路。

前端采用函数式组件与 `useReducer` 全局状态管理，将界面划分为遥测显示、运动控制、数据采集和故障注入四大功能 Workspace。国际化支持中英双语切换，主题支持明暗模式自适应。表 6-1 汇总了 Web 控制台的全部功能。

### 6.2.2 机器人运动控制功能

运动控制模块支持四种输入方式。虚拟摇杆通过界面交互控件实现 X 轴线速度、Y 轴线速度和 Z 轴角速度的三自由度独立调节。键盘控制将 WASD 四键映射为方向指令，空格键映射为紧急停车。Xbox 手柄控制通过浏览器 Gamepad API 读取手柄状态，左摇杆映射平移运动，右摇杆水平轴映射旋转运动。上述三种控制方式的速度指令均经过死区处理与幂函数响应柔化后发送至底层控制器，幂函数指数 `response_exponent` 设为 0.70，在起步响应灵敏度与控制精细度之间取得平衡。

PID 定点巡航是运动控制的高级功能。前端设定目标速度向量后，巡航节点订阅 `/odom` 获取当前实际速度，计算偏差并执行 X/Y 轴 PID 闭环运算输出速度指令。该功能在需要精确控制运动轨迹的数据采集实验中尤为重要。

### 6.2.3 安全保护机制

远程操控机器人存在通信中断、指令延迟等固有风险，Web 控制台设计了五层递进式安全保护机制，从通信层、指令层和执行层三个维度保障操作安全。表 6-2 给出了五层保护机制的详细配置。

**表 6-2 五层安全保护机制**

| 层级 | 保护机制 | 触发条件 | 响应动作 | 参数配置 |
|-----|---------|---------|---------|---------|
| 1 | 心跳超时保护 | 1.0 s 内未收到前端心跳 | 速度指令自动置零 | `heartbeat_timeout = 1.0` s |
| 2 | 指令超时刹车 | 0.5 s 内未收到新速度指令 | 速度线性衰减至零 | `cmd_timeout = 0.5` s |
| 3 | 急停锁存 | `/web/estop` 话题收到急停信号 | 速度强制置零，锁定控制 | 手动解除复位 |
| 4 | 速度硬限制 | 指令速度超过上限 | 速度裁剪至允许范围 | `max_linear = 0.4` m/s, `max_angular = 1.0` rad/s |
| 5 | 死区柔化处理 | 输入幅值低于死区阈值 | 输入置零或幂函数柔化 | `response_exponent = 0.70` |

五层保护机制按优先级递减排列。第一层心跳超时保护在 1.0 秒内未检测到前端心跳时自动将速度置零，防止通信链路断开导致失控持续运动。第二层指令超时刹车在 0.5 秒内未收到新速度指令时触发，响应时间短于心跳超时，处理正常操作停顿场景。第三层急停锁存具有最高人工干预优先级，触发后速度强制置零且控制输入锁定，须手动复位解除。第四层速度硬限制将线速度和角速度上限分别约束为 0.4 m/s 和 1.0 rad/s。第五层死区柔化通过 `shapeAxis()` 幂函数变换消除摇杆零点抖动，使低速段控制平滑。

### 6.2.4 数据采集与文件管理功能

数据采集与文件管理模块基于 HTTP 协议实现，后端服务 `web_dashboard_server.py` 在机器人上位机运行，监听 `:8000` 端口提供 REST API。该模块支持四项核心操作：CSV 文件列表查询、CSV 内容预览、CSV 文件下载和数据集构建。

CSV 文件列表接口返回已采集文件的元信息（文件名、大小、行数、标签分布），预览接口返回前 N 行数据（默认 N = 100），下载接口以二进制流返回文件内容。数据集构建接口调用方指定文件列表和构建参数，后端执行缺失值检查、Z-score 标准化、滑动窗口分割和分层随机划分，输出标准化的 NumPy 数组（.npy）和划分索引文件，该接口将第 4 章的预处理流程封装为可调用的服务。

### 6.2.5 故障注入与故障采样功能

故障注入功能通过 Web 界面配置故障参数并向下位机下发故障配置帧，在受控条件下模拟故障工况。界面提供四个可配置参数：`Fault_Enable`（故障使能标志，0 为关闭，1 为开启）、`Fault_Type`（故障类型选择）、`Fault_Wheel_Mask`（故障作用轮掩码，A 轮 0x01、B 轮 0x02、C 轮 0x04，可组合）以及 `Fault_Alpha`（速度衰减系数，取值 0 至 1.0）。

参数通过 rosbridge 发布至 ROS 话题后，`fault_injector.py` 节点将参数打包为故障配置帧并经 UART 发送至 STM32 控制器。故障采样标记功能与注入协同工作，当故障注入激活时，`data_collector` 自动将 `fault_label` 设为对应标签（1 为 `wheel_slip`，2 为 `drive_abnormal`，3 为 `shaft_eccentric`），无需人工标注，提高了数据集构建效率。

### 6.2.6 Web 端的能力边界

Web 控制台运行于浏览器沙箱环境中，受限于同源策略与本地文件系统访问限制，存在两项固有约束：（1）**无法直接调用本地 C++ 编译的 ONNX Runtime 推理引擎**，因此不具备故障诊断模型推理能力；（2）CSV 文件下载依赖 HTTP 流式传输，大数据量场景下体验弱于本地文件系统直接读写。上述约束决定了 Web 端的定位是**远程实验终端**，而非模型部署终端，也为后续 Electron 桌面端的设计提供了明确的必要性依据。

## 6.3 Electron 桌面端诊断系统设计

桌面端诊断系统并非 Web 控制台的简单替代，而是在其基础上扩展了**模型推理**和**离线数据管理**两大核心能力。系统基于 Electron 框架构建，面向模型部署与实车在线诊断场景，核心目标是突破浏览器安全沙箱对本地推理引擎调用的限制。

### 6.3.1 技术架构

Electron 应用采用主进程与渲染进程分离的经典架构。主进程（`main.js`）负责应用窗口创建与管理、系统菜单配置、原生对话框调用以及子进程生命周期管理。渲染进程（`renderer/`）承载用户界面和业务逻辑，通过 `preload.js` 暴露的安全 IPC（Inter-Process Communication）接口与主进程通信，避免直接暴露 Node.js API 以降低安全风险。`preload.js` 作为两个进程之间的桥梁，仅暴露经过白名单验证的数据库、推理、模型转换和窗口控制 API 方法。

渲染进程采用模块化设计，核心代码涵盖六个子模块：连接管理（WebSocket 连接与自动重连）、遥测显示（ROS 话题订阅与状态渲染）、驾驶控制（摇杆与键盘输入）、采集管理（`data_collector` 启停控制）、实验流程（故障配置与自动化脚本）和诊断可视化（推理结果实时渲染）。界面采用 VS Code 风格的侧边栏-工作区布局，支持 Dashboard、Drive、Charts、Collect、Experiment 和 Settings 六个视图切换。

### 6.3.2 推理引擎集成

推理引擎是桌面端区别于 Web 端的核心技术特征。系统采用 ONNX Runtime C++ 后端，以独立子进程形式运行。推理服务（`inference-service.js`）在主进程中通过 `child_process.spawn` 启动 `yp_fault_infer.exe`，该可执行文件为 C++ 编译的 ONNX Runtime 推理引擎，加载位于 `models/sage_cnn/` 目录下的模型包。

模型包包含三个核心文件：ONNX 模型文件（`.onnx`）、训练阶段拟合的 `StandardScaler` 参数文件（`scaler.json`）以及描述输入输出规格的清单文件（`manifest.json`），便于模型的版本控制和分发部署。推理服务通过 JSON-RPC（JavaScript Object Notation - Remote Procedure Call）协议与渲染进程通信：渲染进程将标准化后的滑动窗口数据序列化为 JSON，经 IPC 发送至主进程，主进程通过标准输入（stdin）写入推理子进程；子进程执行前向推理后，将分类 logits 和置信度分数经标准输出（stdout）以 JSON 行形式返回。

该设计将模型推理计算隔离在独立进程中，避免推理任务阻塞渲染进程主线程，即使推理子进程崩溃也不会导致整个 Electron 应用卡死。渲染进程通过 `window.electronAPI.inference.*` 接口调用加载模型、执行预测、查询后端状态等操作，实现了业务逻辑与推理计算的解耦。

### 6.3.3 离线数据管理与实验记录

桌面端通过 `better-sqlite3` 模块建立本地 SQLite 数据库，存储于操作系统用户数据目录（Windows 下为 `%APPDATA%/YP-telemetry-dashboard`），实现实验历史、数据集构建记录和连接日志的持久化管理。数据库表结构涵盖连接历史（`connections`）、数据集构建任务（`dataset_builds`）、实验记录（`experiments`）和实验事件（`experiment_events`）四张核心表。

该能力使桌面端具备完全的离线运行特性：即使断开与机器人的网络连接，用户仍可浏览历史实验、查看过往诊断结果、管理本地数据集。Web 端因浏览器沙箱限制无法直接读写本地文件系统，必须依赖 HTTP API 获取数据，在离线场景下完全不可用。

## 6.4 双端功能对比与互补关系

Web 远程控制台与 Electron 桌面端诊断系统共用 ROS 通信后端，但承载于完全不同的技术架构之上，形成功能互补而非相互替代的关系。表 6-3 从架构、通信、功能和场景四个维度给出详细对比。

| 技术架构 | B/S（浏览器/服务器） | C/S（本地客户端/服务器） |
| 前端框架 | React 18 + Vite | 原生 HTML/JS + Electron |
| 页面加载 | HTTP `:8000` 远程加载 | `file://` 本地文件加载 |

| 运动控制 | 虚拟摇杆/键盘/手柄/PID 巡航 | 虚拟摇杆/键盘/手柄 |

两套系统的功能边界清晰：Web 端胜在**零部署、跨设备**，适合实验室多人协作与快速验证；Electron 端胜在**原生能力、离线推理**，适合现场实车长期监测。Electron 端新增的 ONNX 推理子进程和 SQLite 数据库是两者功能差异的技术根源。在实际部署中，研究人员可通过 Web 端完成故障样本采集与标注实验，再通过 Electron 端加载训练好的模型执行在线诊断，形成"实验-训练-部署-诊断"的完整闭环。

## 6.5 在线诊断流程设计

在线诊断流程定义了从传感器数据采集到诊断结果可视化的完整数据链路，仅在 Electron 桌面端实现，须保证推理阶段的预处理操作与训练阶段严格一致。流程共包含七个阶段。

第一阶段为传感器数据采集。底盘数据以约 20 Hz 频率上报至 ROS 话题，包括 `/odom`（里程计速度，3 通道）、`/wheel_speed`（三轮轮速，3 通道）、`/imu`（三轴角速度与三轴加速度，6 通道）和 `/current_data`（三通道电流，3 通道），共计 15 个数据通道。

第二阶段为数据同步与记录。`data_collector` 节点以 `/odom` 话题到达为时钟触发信号，同步采样其余话题最新值，组合为一条 45 字段的 CSV 记录并实时落盘。

第三阶段为数据预处理。Electron 应用读取原始传感器数据，加载训练阶段保存的 `StandardScaler` 参数，对各通道执行 Z-score 标准化：

$$
x'_i = \frac{x_i - \mu_i}{\sigma_i}
$$

其中 $x_i$ 为第 $i$ 通道原始值，$\mu_i$ 和 $\sigma_i$ 分别为该通道在训练集上的均值和标准差。使用训练集参数而非在线计算参数，确保推理数据的分布变换与训练数据一致。

第四阶段为滑动窗口构建。采用与训练阶段相同的窗口参数：窗口大小 `window_size = 50`（对应 2.5 秒），步长 `step_size = 10`（相邻窗口重叠 40 个时间步）。每个窗口组织为 $[15, 50]$ 的二维张量，15 为传感器通道数，50 为时间步长。

第五阶段为模型推理。预处理后的窗口数据经维度扩展形成 $[N, 15, 50]$ 的批次张量（$N$ 通常为 1），送入 ONNX Runtime 执行前向推理。模型输出 4 维 logits 向量，对应正常、打滑、驱动异常和轴偏心四个类别。

第六阶段为部署守卫后处理。logits 经 Softmax 转换为概率分布后，依次通过四重后处理机制：静止门控（速度低于阈值时强制输出正常）、低置信度过滤（最高概率低于阈值时标记不确定）、模糊保护（top-2 概率差值过小时拒绝判定）和滑动窗口投票（连续多个窗口结果多数投票输出稳定标签）。部署守卫的详细设计已在第 5.5.3 节阐述。

第七阶段为结果可视化。最终诊断结果（类别标签、置信度分数、建议操作）通过 IPC 推送至渲染进程，前端界面实时更新诊断状态面板，显示当前诊断类别、各类别概率条形图、历史诊断趋势曲线以及故障操作建议文本。

## 6.6 故障响应策略

在线诊断系统检测到故障后，根据故障类型和置信度等级执行分级响应策略。响应策略的设计原则为：故障置信度越高，响应措施越主动；故障对安全的潜在威胁越大，响应速度越快。

诊断结果分为三个置信度等级。高置信度（最高类别概率大于 0.90 且 top-2 差值大于 0.30）表示模型判定具有较强把握，系统立即执行对应响应动作。中置信度（最高类别概率介于 0.75 至 0.90 之间）表示判定较为可靠但存在一定不确定性，系统以醒目视觉标识提示操作人员关注并记录诊断日志。低置信度（最高类别概率低于 0.75 或触发模糊保护）表示模型判别信心不足，系统输出"判定不确定"提示，不执行自动化响应动作，依赖人工判断。

对于高置信度故障，响应按类型分级：轮子打滑显示警告并建议降速或更换地面，同时记录时间戳和传感器快照；驱动异常自动降低最大允许速度 50%；轴偏心触发最强响应，降低速度限制并发出声光报警。

紧急停车（Emergency Stop）是优先级最高的处置措施，触发条件包括手动急停按钮和部署守卫检测到严重故障自动触发两种。紧急停车立即向 `/cmd_vel` 发布零速度指令并切断电机 PWM 输出，急停状态具有锁存特性，须通过复位按钮显式解除。所有诊断结果和响应动作自动记录至日志 CSV 文件，为后续分析提供结构化历史数据。

## 6.7 本章小结

本章围绕可视化系统与实车诊断平台的设计展开详细论述，明确了"先 Web、后桌面"的两阶段演进路线。

Web 远程控制台采用 B/S 架构，前端基于 React 18 + Vite 技术栈，通过 rosbridge WebSocket 实现与 ROS 后端的实时通信，并借助 HTTP `:8000` 服务提供 CSV 文件管理接口。系统实现了运动控制、安全保护、数据采集管理和故障注入四项核心功能：运动控制提供虚拟摇杆、键盘、Xbox 手柄和 PID 巡航四种输入方式；安全保护设计了心跳超时、指令超时刹车、急停锁存、速度限制和死区柔化五层递进式机制。同时，本章明确界定了 Web 端的能力边界——受浏览器沙箱限制，无法调用本地 C++ 推理引擎，不具备故障诊断能力。

Electron 桌面端诊断系统采用 C/S 架构，基于 Electron 主进程-渲染进程分离架构构建。推理引擎以 ONNX Runtime C++ 子进程独立运行，通过 JSON-RPC 协议与渲染进程通信，模型包包含 ONNX 权重、`StandardScaler` 参数和清单文件，便于版本控制与分发。本地 SQLite 数据库实现了实验历史与数据集构建任务的持久化管理，使系统具备完全的离线运行能力。

在线诊断流程定义了从传感器采集、标准化、滑动窗口构建、模型推理、部署守卫后处理到结果可视化的七阶段数据链路，确保训练与推理预处理严格一致。故障响应策略依据置信度等级实施分级处置，涵盖警告提示、速度限制和紧急停车等措施。

上述平台将第 5 章训练的 SAGE-CNN 模型与第 3 章的系统硬件架构有机集成，形成从数据采集到智能诊断再到结果呈现的完整闭环系统，为第 7 章的实车系统测试提供了操作界面和功能基础。
